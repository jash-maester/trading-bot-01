# Integration pass — durable evidence

Written during the cross-stream integration of R4/R5/R6/R8, after four
adversarial verifiers returned FAIL on all four streams.

Every number below either cites a file in this repo, a command you can re-run,
or is explicitly marked **UNVERIFIED** / attributed to whoever measured it.
Nothing here is a result about the model. Per CLAUDE.md rule 2, no artefact in
this directory may be described as a winner, baseline-beating, or validated:
there is no MLflow run ID behind any of it.

---

## 1. The R4 smoke run

**Regenerate:**

```
uv run python scripts/smoke_signal.py --out audit/smoke_signal
```

Runs on CPU, uses no GPU, and takes a few seconds. The panel is synthetic
(`tests/fixtures/synthetic_panel.py`, `signal_strength=0.0` — pure noise, no
planted signal). Committed output: `audit/smoke_signal/{gate.json,
index.json, predictions.parquet, summary.json}`. `embeddings.npy`,
`signal_model.pt` and the per-window splits are regenerated by the command and
are not committed.

**What it demonstrates.** The verdict is `FAIL`, and the two reasons are the
two gate defects this pass fixed:

```
"w1 h=5: 95% CI [-0.0202, +0.1669] includes zero"
"w1 h=20: only 4 scorable OOS day(s), need >= 30 (skipped: 56 thin, 0 degenerate)"
```

The `h=20` line is the important one. That horizon scored **mean IC 0.30 on 4
days**, with a CI of `[0.300, 0.300]`. Under the previous gate — mean IC above
0.02 *and* a CI excluding zero, with no floor on the number of days — that
combination **passed outright**. It now fails, by name, and the 56 unscorable
days are reported rather than silently dropped.

This is a synthetic fixture. The 0.30 is an artefact of scoring four days; it
is not a measurement of anything.

## 2. The gate's confidence interval is not a 5% test

`bootstrap_mean_ci` (`src/trader/training/supervised.py`) now resamples
contiguous blocks of `h` days rather than individual days, because consecutive
daily ICs are not independent: `h`-day forward returns overlap, and a fitted
signal is persistent day to day.

Measured false-positive rate under a strict null (i.i.d. returns, a predictor
carrying zero information, 150 names × 250 OOS days, 300 trials):

| horizon | IC lag-1 ACF | i.i.d. bootstrap | moving-block (block = h) | nominal |
|---|---|---|---|---|
| h = 5  | +0.73 | 38.0% | 11.6% | 5% |
| h = 20 | +0.88 | 62.0% | 15.7% | 5% |

A large improvement, and **still not a 5% test**. It cannot be made one by
choosing a better block length — sweeping block ∈ {h, 10, 20, 30, 40, 50, 60}
plateaus at ~16% for h=20, and a Newey–West HAC interval with an
autocorrelation-derived effective df lands at 13.6% on the same data. The
reason is sample size, not method: at ACF +0.88 a 250-day window carries an
effective sample size of roughly **16 days**, and no reweighting of 16
effective observations yields a well-calibrated interval.

`HorizonMetrics` therefore carries `ic_acf_lag1` and `n_eff`, and `gate.json`
reports both per horizon, so a reader can see what the interval is worth.

**Consequence for the run queue:** treat `ci_lo > 0` as a necessary screen, not
as evidence. A PASS resting on it alone — mean IC barely above the bar, `n_eff`
in the tens — is not a validated signal.

The i.i.d./persistent false-positive figures above were first measured by the
adversarial verifier of stream R4 and independently reproduced during this
pass (38.0% / 62.0% here against their 33.7% / 63.0%; same conclusion, and the
difference is the predictor's persistence parameter, which neither run pinned).

## 3. Compute: do NOT pin `device=cpu`

The R4 build report claimed the full-width config "did not finish in 10 minutes"
on MPS and advised falling back to CPU. That advice is **wrong** and was never
committed to a config — `configs/train/supervised.yaml` ships `device: auto`,
which is correct and should stay.

Measured by the R4 verifier at the shipped shape (embed_dim 128, num_channels
[128,128,128,128], N=504, L=30, F=15), one full optimiser step:

| batch_days | CPU | MPS | |
|---|---|---|---|
| 32 | 22,524.9 ms | 2,831.2 ms | MPS **8.0× faster** |
| 8  |  6,225.8 ms |   572.5 ms | MPS **10.9× faster** |

**UNVERIFIED by this pass** — reproducing it means running a training step on
the GPU, which this integration pass was explicitly forbidden from doing. It is
recorded here so the run queue does not inherit the opposite advice.

If a full-width run does stall, the likely cause is activation memory at
`batch_days=32` (a `[32,504,128,30]` float32 activation is ~2.5 GB per TCN
layer), which is fixed by lowering `batch_days` — not by moving to CPU. That
matches the MEMORY.md note about never running a spilling setup.

## 4. What the seam tests cover

`tests/integration/test_cross_stream_seams.py` — 14 tests, all on synthetic
data, no GPU:

| seam | what it proves |
|---|---|
| a | R4 writes the pinned artefact set with the pinned schema (f64, one row per (date, ticker), axis-1 order); R5's real readers + real `allocate()` turn it into weights that respect both caps |
| b | R6's `EmbeddingCache` opens R4's directory, and the sha guard refuses both a bogus hash and a real differently-initialised encoder |
| c | R6's `AllocatorEnv` calls R5's real `allocate()` (verified by counting calls through the real import), one step advances one rebalance period (never 1 day), and an inner env with no schedule is refused |
| d | `train_allocator_rl.require_passing_gate` refuses FAIL and proceeds on PASS — **both directions**, plus an incomplete artefact set; `run_allocator._read_gate` likewise |
| e | `FEATURE_COLS` is unchanged (15 columns), the ext group is disjoint, and R4's predictions are **bit-identical** when unused ext columns are added to the panel |

Seam (d) tests both directions deliberately: a gate that always refuses looks
identical to a working one if you only test the refusing direction.

## 5. Known remaining gap — not fixed, needs a decision

`materialise_window` gives the test split no warm-up prefix, so the first
`lookback - 1` days of every OOS segment produce no prediction.

At the shipped config (`configs/walk/default.yaml`: 4 windows × 12 test months;
`lookback: 60`) that is **59 days lost per window, 236 of ~1005 OOS days —
23.5%**. Regenerate with:

```
uv run python -c "
from trader.training.walk_forward import compute_windows
from datetime import date
w = compute_windows(date(2005,4,1), date(2026,9,1), train_years=5, val_months=12,
                    test_months=12, purge_months=3, n_windows=4, step_months=12)
print(sum((x.test_end - x.test_start).days * 252 // 365 for x in w))"
```

This is a loss of statistical power, **not** a contamination bug: the current
behaviour is the conservative one. Fixing it means feeding the encoder
`lookback - 1` rows of feature history from the purge gap while excluding those
rows from both label construction and scoring. That touches the OOS scoring
path, where a mistake *is* contamination, so it was left alone rather than
changed at the end of an integration pass.

**Decision needed:** whether to add a warm-up prefix that is feature-context
only. If yes, it needs its own change with its own test proving the warm-up
rows are never scored and never labelled.
