# P4 — bounding the survivorship bias

Written 2026-09-06. Scope: `11_cost_defect_and_fix_plan.md` §P4, which defers
survivorship as "the live confound" and forbids quoting absolute CAGR until it
is addressed. This report does **not** lift that restriction. It splits the
concern into three parts, proves one of them is already handled, builds the
measurement arm for the second, and states the third as unrecoverable.

Nothing here was run on the GPU and no backtest was run. Every number below is
regenerated by one of two commands, both quoted in place.

**Verdict, in one line:** the mechanical look-ahead is prevented and now tested;
the post-hoc *listing* selection is measurable and the arm to measure it is
written but **not yet run**; the *delisting* bias is unrecoverable from this
data and cannot be bounded — the panel contains 645 names and zero deaths.

---

## 1. What is already prevented, and the test that proves it

### The claim

A name that has **never been tradeable** can never acquire weight: `allocate()`
returns exactly 0.0 for it, on every date. A name is `is_tradeable=False` before
it lists, so "the model traded a stock before it existed" is not a live defect.

**That is the narrow claim, and only the narrow claim.** An earlier version of
this section said `allocate()` "cannot put weight on a name on a date the panel
marks `is_tradeable=False`", which is FALSE on the default path and was refuted
in review. The mask gates *candidacy*, not *holdings*: a name already held that
becomes untradeable is not sold to zero in one step, because `turnover_budget`
scales the exit like any other trade. Measured with `AllocatorParams()`
(band 0.0, turnover budget 0.30):

| start | after one rebalance |
|---|---|
| five names at 0.2 each, all become untradeable | cash 0.30, **0.14 x5 still held** |
| one held name of five becomes untradeable | it keeps 0.10 of NAV |
| with `no_trade_band >= its weight` | pinned at its current weight indefinitely |

Reproduce with `tests/unit/test_listing.py::test_a_held_name_that_becomes_
untradeable_is_not_liquidated_in_one_step`.

This is harmless **here** only because the panel contains zero delistings — no
name ever goes permanently untradeable — and it becomes live the moment §4's
point-in-time repair lands, since a delisted name is exactly a held name whose
mask goes to False and stays there.

### Why it holds — three independent belts, all verified (two load-bearing)

**Belt 1 — the panel.** `align_panel` computes each ticker's
`[first_date, last_date]` from the OHLCV it was handed, nulls every price
outside that span, and sets `is_tradeable = adj_close.is_not_null()`
(`src/trader/data/alignment.py:53-74`). A pre-listing date therefore cannot be
tradeable by construction. `compute_features` then *further* clears the flag on
any row where a rolling feature is still null (`src/trader/data/features.py:212-221`).

Measured on `data/panels_kite/full.parquet` — the mask is strictly more
conservative than the presence of a price bar, for all 645 names:

| first-tradeable minus first price bar, calendar days | value |
|---|---|
| count | 645 |
| min | +81 |
| median | +87 |
| mean | +123.1 |
| max | +2966 |
| names where the mask precedes the first price bar | **0** |

The median +87 calendar days is the 60-trading-day feature warm-up.

## 3. The restricted arm — what it will and will not answer

### What was built

`scripts/survivorship_arm.py` writes a panel split restricted to names that were
already trading well before the backtest starts. `src/trader/data/listing.py`
supplies `first_tradeable_dates` and `eligible_at`, both pure functions over a
polars frame.

```
uv run python scripts/survivorship_arm.py --dry-run    # census, writes nothing
uv run python scripts/survivorship_arm.py              # writes the split
```

Defaults: restrict `oos` to names with **>= 252 tradeable days strictly before
2014-12-31**, eligibility judged on `full.parquet`. Eligibility must be read off
the full panel — the OOS split begins in 2016 and holds no pre-2014 history, so
asking it would return nothing; the script refuses that combination rather than
silently returning an empty universe.

Output, `data/panels_kite/oos_pre2015.parquet`
(SHA256 `52fc70440f543002f1ffec34bb655ccacb0957f59cdec761cd84c803fb67e9a5`,
stable across reruns; ticker list in `oos_pre2015.manifest.json`):

| | full `oos` | restricted |
|---|---|---|
| tickers in the split | 645 | **360** |
| of `active_tickers()` (504, the env's traded width) | 504 | **277** |
| rows | 1,239,045 | 691,560 |
| tradeable rows | 901,934 | 691,013 |
| tradeable names/date, **panel-wide (645)** — mean | 469.5 | 359.7 |
| tradeable names/date, **panel-wide (645)** — min / max | 385 / 570 | 356 / 360 |
| tradeable names/date, **env universe (504)** — mean | **364.9** | **276.7** |
| tradeable names/date, **env universe (504)** — min / max | 297 / 443 | 273 / 277 |

**The two blocks count different universes and only the second one is traded.**
`run_allocator.py` builds the env universe from `active_tickers()` = 504, so 141
of the panel's names are never held by either arm; a panel-wide breadth figure
understates how selective `k=30` is. The allocator's true candidate pool
(`mask & finite r_hat & vol > 0 & sector_id > 0`) gives the same 365.0 -> 276.7.
Both lines are printed by `--dry-run`, so neither can be quoted without the
other.

The restriction binds through the mask, not through a new code path:
`run_allocator.py:291` builds the env universe from `active_tickers()`, not from
the panel, and `PanelTradingEnv` leaves a universe ticker with no panel rows as
an all-zero column — mask `False` on every date. So the arm is enforced by
exactly the belt §1 tests, and both arms lose the same names.

### One thing that had to be fixed before the arm could run — now applied

`run_allocator.py` logged `"universe_size": len(universe)` to MLflow, and
`universe` is always `active_tickers()` — 504 — regardless of split. A
restricted run would therefore have been tagged `universe_size=504` while
actually trading 277 names, and the restricted and unrestricted runs would have
been indistinguishable by their MLflow params: a run ID that does not say what
it ran (CLAUDE.md rule 2).

**Fixed in the integration pass.** Every arm now also logs
`universe_effective` — the count of `active_tickers()` that have rows in the
split — so a restricted run reads `universe_size=504, universe_effective=277`
and an unrestricted one reads `504 / 504`. The script prints the same line at
startup.

### What it will answer — and the decision rule, pre-registered

Whether the allocator's edge over equal-weight survives when **no name selected
after 2014 is in the universe at all**. If monthly K=30/20d still beats
equal-weight on the restricted arm, post-hoc listing selection is not what
generates the edge. That is the whole claim; it is a sensitivity, not a
correction.

**The threshold is fixed here, before the arm runs**, because "a comparable
margin" with no number attached is how a sensitivity becomes a "pass with
caveats" (CLAUDE.md forbids exactly that, and limit 3 below pre-declares a lower
allocator CAGR as uninformative — between them, without a number, no result
could ever fail).

Let `G = CAGR(allocator) - CAGR(equal_weight)` **within one arm**, at monthly
K=30 / 20d, both arms run through the same env with the same seed.

* `G_unrestricted` is the standing figure, **+0.192** on `oos_r4_v2`
  (`audit/R4_R5_RESULTS.md`). It must be re-measured, not reused, if the code
  has moved since — and it has: see the note at the end of this section.
* **P4 records PASS iff `G_restricted >= 0.5 · G_unrestricted` and
  `G_restricted > 0`.** At the standing numbers that is `G_restricted >= +0.096`.
* **P4 records FAIL if `G_restricted < 0.5 · G_unrestricted`**, including if it
  is negative. A fall in the *absolute* CAGR of either arm is not a failure and
  is not evidence of anything (limit 3); only the gap counts.
* Half is a choice, not a law. It is set where it is because the restriction is
  not one-factor — breadth, sector mix and cohort return all move (limits 2 and
  3) — so a gap that merely narrows is consistent with the edge surviving, while
  a gap that halves is not distinguishable from one the restriction erased.
* The null-signal control runs on the restricted arm too. If
  `CAGR(null) - CAGR(equal_weight)` moves by more than `G` does, the restriction
  changed the machinery rather than the selection, and **neither** verdict is
  admissible.

### What it will not answer — four limits, all load-bearing

1. **It does not remove delisting bias.** All 360 kept names are still 2026
   survivors. See §4.
2. **It is not a one-factor change**, in three separate ways.

   (a) **Breadth.** On the universe the env actually trades, breadth falls from
   364.9 to 276.7 names per date, so at a fixed `k=30` the allocator becomes
   *more* selective: **8.22% → 10.84%** of the cross-section, and 88.1 names per
   date leave the pool. (Panel-wide the same restriction reads 469.5 → 359.7 and
   6.4% → 8.3%; that row counts 141 names neither arm can hold and understates
   k/N by ~2.5 percentage points.)

   (b) **Sector composition.** The restriction keeps 49%–86% of names per
   sector, not a uniform fraction, so `max_sector_weight=0.25` binds on a
   different mix and not merely a smaller one:

   ```
   sector retention (env universe): 1: 107->53 (50%), 2: 32->19 (59%),
     3: 59->29 (49%), 4: 43->31 (72%), 5: 38->31 (82%), 6: 19->13 (68%),
     7: 42->30 (71%), 8: 22->19 (86%), 9: 81->52 (64%)
   ```

   (c) **Phantom sectors.** 227 of the 504 active tickers have no rows in the
   restricted split and become all-zero env columns with `sector_id == 0` — an
   id absent from `SECTOR_IDS`. Harmless for the allocator (`sector_ids > 0`
   excludes them) and for equal-weight (mask only), but this is CLAUDE.md's
   known-dangerous phantom-sector condition: **`oos_pre2015.parquet` must never
   be handed to a graph model.** Printed on every run of the arm.
3. **The dropped cohort is the higher-returning one**, so both arms should fall
   in absolute terms and a lower allocator CAGR is expected rather than
   informative. Equal-weight cross-sectional daily log return over the OOS span,
   annualised (from `--dry-run`):

   | cohort | names/date (panel-wide) | log return | ~CAGR | ann vol |
   |---|---|---|---|---|
   | kept (pre-2015) | 359.7 | +0.1790/yr | +19.6% | 0.1915 |
   | dropped (post-2014) | 109.8 | +0.2080/yr | +23.1% | 0.1869 |

   The `names/date` column here is **panel-wide**; on the env universe the same
   two cohorts are 276.7 kept and 88.1 dropped. The return figures are
   cross-sectional means over the panel-wide cohorts and are unchanged.

   **The comparison to read is allocator-minus-equal-weight *within* the
   restricted arm, against the same difference in the unrestricted arm.** Any
   absolute CAGR from either arm remains unquotable under §P4.
4. **Sector ids are still 2026 classifications.** `sector_id` comes from
   `SECTOR_MAP` as it stands today and is applied to every historical row. The
   sector cap (`max_sector_weight=0.25`) therefore binds on a hindsight
   taxonomy. The restricted arm does not touch this, and it is not in scope for
   any file this stream owns.

More importantly, the split that exists on this machine is **not** the one the

```

Comparing a restricted **r4_v1** arm against the unrestricted **r4_v2** table
would confound the restriction with the warm-up-prefix coverage change that
`audit/R4_R5_RESULTS.md` already attributes 10 CAGR points to. Do not do it.

## 4. The delisting bias — unrecoverable, and it cannot be bounded

### The measurement

Every one of the 645 tickers in `full.parquet` is tradeable on the panel's last
date, 2026-09-04. Not most of them — all of them:

```
distinct last-tradeable dates across 645 tickers: 1
that date: 2026-09-04
tickers whose last tradeable date is earlier: 0
```

`survivorship_arm.py` prints this on every run so it cannot be dropped from a
write-up:

```
UNRECOVERABLE: 645 of 645 tickers are still tradeable on 2026-09-04
(0 deaths in 2005..2026). Restricting the listing side does not fix this.
```

A real Indian equity universe over 2005-2026 delists names — suspensions,
compulsory delistings, mergers, acquisitions. **Zero deaths in 21 years is the
signature of a set enumerated from a current instrument dump**, and it is a
sharper statement of the problem than CLAUDE.md's "the universe is not
point-in-time".

### Why it cannot be recovered here

`market.universe_snapshots` would have held point-in-time membership. Verified
against the live database:

    -U "$POSTGRES_USER" -d "$POSTGRES_DB" \

```

> **Corrected 2026-09-06.** The block above previously showed a three-column
> `rows | min | max` header under a `select count(*)`, which that query cannot
> produce: the transcript was invented, though the fact it stated was true. A
> fabricated command output in `audit/` is precisely what the CLAUDE.md
> verification standard exists to prevent, so it is recorded here rather than
> quietly replaced.

CLAUDE.md's entry is accurate, with one refinement worth recording: there **is**
a write path — `scripts/build_universe.py:48-67` inserts a `UniverseSnapshot`
row — but it writes a single row at the date it is run, so even if executed it
would record today's membership, not history. And there is still **no read site
anywhere in `src/` or `scripts/`**: the only other references are the alembic
migration, the ORM class, and `tests/integration/test_db_roundtrip.py`. The
table cannot be backfilled from anything in this repository, because the only
symbol source here is the same 2026 dump.

### Direction

**Upward on every absolute return in every arm.** A name that delisted between
2016 and 2024 contributes nothing to any backtest here, and the realised
cross-section is conditioned on survival to 2026. Symbol renames make it worse
rather than better: CLAUDE.md's `LTIM→LTM`, `TATAMOTORS→TMPV`, `MCDHOLDING`
delisted are cases where a symbol-keyed join drops history silently, so some
"absent" names are absent for a reason unrelated to their returns, and the
direction of that subset is unknown.

### Magnitude

**Cannot be bounded from this data.** This is not a hedge, it is what the
measurement above forces: the panel contains **zero** delisted names, so it
carries no sample at all of the distribution that is missing. Any figure for the
size of the bias would have to be imported from outside the repository — an NSE
delisting history, or a vendor's point-in-time index membership — and neither is
present. Under CLAUDE.md rule 3, a confident guess is not an acceptable
substitute; "UNVERIFIED" is.

Two things would change this, in increasing order of cost:

1. An NSE delisted-securities list joined by symbol and date would give a
   **count** of missing names per year — enough to bound the *breadth* of the
   hole, though not the return attached to it.
2. Point-in-time NIFTY membership (an index-provider file, or archived NSE
   circulars) backfilled into `market.universe_snapshots` with a read site in
   `universe.py` would fix the problem outright rather than bound it. That is
   the only real repair, it needs an external data source, and it is out of
   scope for every file this stream owns.

### Does the bias cancel in the allocator-vs-equal-weight comparison?

Partly, and the "partly" matters. Both arms draw from the same survivor set
through the same mask, so a first-order survivorship lift applies to both and
largely cancels in the difference — which is why `audit/R4_R5_RESULTS.md` is
right that the comparison is more trustworthy than any CAGR in it.

**The argument this section used to make for the residual's sign was wrong.** It
said equal-weight holds ~470 names and the allocator holds 30, so the allocator
is more exposed to the tail. Two things are wrong with that. First the number:
equal-weight reads `obs["mask"]` over `active_tickers()` = 504, not over the
645-name panel, so it holds **~365** names per date (min 297, max 443), not 470.
Second, and worse, the *form* of the argument: concentration is a statement
about **variance**, and variance alone produces no bias in a difference of
means. Holding 30 names instead of 365 makes the allocator's return noisier, not
systematically higher.

What actually sets the sign is the rate at which the truncated names — the left
tail — would have been **picked**, against the rate at which they sit in the
benchmark. Equal-weight's rate is the population share by construction. The
allocator's is measurable on the data that exists:

```
uv run python scripts/survivorship_arm.py --dry-run \
    --tail-exposure data/signal/r4_v1

tail exposure (1488 dates, top-30 by r_hat_20d vs realised forward 20d return):
  in the bottom decile: 11.16% of picks (a rate-blind pick would be 10%) -> 1.12x
  in the bottom 5%:      6.26% of picks (a rate-blind pick would be 5%)  -> 1.25x
```

So the selection leans mildly *into* the left tail — 1.1-1.3x the population
share, not the 365/30 = 12x the concentration argument implied — and the
residual therefore runs **upward for the allocator relative to equal-weight**.

**The sign is supported; the magnitude remains UNVERIFIED and is not
recoverable here.** The tail measured above is realised forward return *inside*
the panel, and the names survivorship removed are not in the panel at all (zero
deaths). A 1.12x over-exposure to an unobserved tail bounds nothing. State the
gap as the result; do not state it as bias-free.
